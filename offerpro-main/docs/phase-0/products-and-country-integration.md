# Products Catalogue & Sales by Countries — the fixed points

**Phase 0 · decision document. These two features are frozen. Everything else accommodates them.**

Both are already built. Neither is to be removed, refactored or redesigned. This document
records exactly what they touch, so that later phases can be planned around them instead of
into them.

---

## 1. What is actually built

### Products catalogue — `0011_product_catalog.sql`

| Artefact | Detail |
|---|---|
| Table | `catalog_items` — **not** `products`. `public.products` (`0001_init.sql:328`) is ProductPlanner's roadmap and has no price, SKU or tax. `0011`'s header documents the split |
| Operator columns | `name`, `sku`, `description`, `category`, `unit_price`, `unit`, `hsn_sac`, `tax_rate`, `track_inventory`, `stock_qty`, `low_stock_at`, `archived_at` |
| **Trigger-owned columns** | `units_sold`, `revenue`, `revenue_paid`, `invoice_count`, `last_sold_at` |
| Link to sales | `document_line_items.catalog_item_id uuid references catalog_items(id) on delete set null`, index `line_items_catalog_idx` |
| Definitions | `app.catalog_is_sold(type, status)` — invoices only, in `sent`/`viewed`/`partially_paid`/`overdue`/`paid`/`payment_submitted`. `app.catalog_is_collected(type, status)` — invoices with status `paid` |
| Rollup | `app.recompute_catalog_sales(item)`; triggers `line_items_catalog_rollup` (AFTER ins/upd/del on line items) and `fin_docs_catalog_rollup` (AFTER UPDATE OF status, issue_date, with a `when` guard). Repair: `app.rebuild_catalog_sales(org)` |
| Date-ranged report | `public.catalog_performance(p_org, p_from, p_to)` — SECURITY DEFINER with an `app.is_member(p_org)` gate |
| Privilege model | Table-wide `revoke update ... from authenticated`, then a **column-list `grant update`** covering only the operator columns. The rollups are unwritable from the browser |
| RLS | member select / writer insert & update / admin delete; `enable` **and** `force` |
| Client | `src/services/catalogService.js`, `src/components/Products.jsx` (667 lines), `src/components/shared/ProductPicker.jsx`, `orgStore.SECTIONS.catalog` |
| AI | `companyMemory.ts` `formatCatalog()` — reads the trigger-maintained rollups rather than deriving totals |

### Sales by Countries — `0012_country_codes.sql` + `0013_sales_by_country.sql`

| Artefact | Detail |
|---|---|
| Reference table | `country_codes (code char(2) pk, name, aliases text[])` — generated by `scripts/generate-country-seed.js` from `i18n-iso-countries`. RLS on, `select` true for authenticated, **no** insert/update/delete policy |
| Provenance enum | `country_source` — `customer`, `org_default`, `manual`, `checkout_form`, `checkout_geoip` |
| Columns added | `organizations.country_code`, `customers.country_code`, `financial_documents.country_code`, `financial_documents.country_source` — all FK to `country_codes(code)` |
| Indexes | `customers_country_idx (org_id, country_code)`; `fin_docs_country_idx (org_id, country_code, issue_date desc)` |
| Resolution | `app.country_from_state(text)` (Indian states → `IN`), `app.country_code_from_name(text)` (free text → code via `aliases`), `app.resolve_document_country(org, customer, state)` — a five-step confidence chain |
| Trigger | `fin_docs_set_country` **BEFORE INSERT**, and it **no-ops when `country_code` is already supplied**, stamping `country_source = 'manual'` in that case |
| Aggregation | `public.sales_by_country(p_org, p_from, p_to, p_catalog_item)` → `iso2, revenue, collected, pipeline, doc_count, customer_count, prev_revenue`. SECURITY DEFINER, `app.is_member(p_org)` in the `WHERE` |
| Client | `src/services/salesGeoService.js`, `src/components/dashboard/SalesByCountries.jsx`, `src/data/worldMap.js` (generated by `scripts/generate-world-map.js`), `src/components/shared/CountrySelect.jsx` |
| Mounted at | `src/components/Dashboard.jsx:224` |

## 2. Which finance tables they touch

Both features are **read-side consumers of the finance schema**, plus exactly two writes.

| Table | Products catalogue | Sales by Countries |
|---|---|---|
| `financial_documents` | **Reads** `type`, `status`, `issue_date`, `id` — via `app.catalog_is_sold` / `is_collected`. **Trigger** `fin_docs_catalog_rollup` fires on status/issue_date change | **Writes** `country_code` + `country_source` on INSERT (`fin_docs_set_country`). **Reads** `grand_total`, `type`, `status`, `issue_date`, `customer_id`, `org_id` |
| `document_line_items` | **Owns** the `catalog_item_id` column. **Trigger** `line_items_catalog_rollup` on every insert/update/delete | **Reads** `line_total` and `catalog_item_id` when the widget is filtered to one product |
| `customers` | — | **Reads** `country_code` and `state` inside `app.resolve_document_country()` |
| `organizations` | — | **Reads** `country_code` as the fallback default |
| `payments` | Indirect only — `payments` sets `financial_documents.status` to `paid` via `app.recompute_amount_paid()`, which fires `fin_docs_catalog_rollup`, which moves `revenue_paid` | Indirect, same chain: `collected` is `status = 'paid'` |
| `expenses` | — | — |
| `recurring_invoices` | Not linked. Its `items jsonb` array has **no** `catalog_item_id` (see §4.1) | Not linked. Generated invoices get their country from the trigger like any other |

**The critical shared dependency:** both features' definitions of a sale are the *same two
functions*. `sales_by_country()` calls `app.catalog_is_sold()` and
`app.catalog_is_collected()` directly (`0013:262`, `:268`). **Changing either function
changes both the Products page and the Sales map simultaneously.** That is deliberate —
`0013`'s comment says keeping one meaning for "revenue" across three screens matters more
than a bigger number on one — and it means those two functions are effectively public API.

**Rule: `app.catalog_is_sold` and `app.catalog_is_collected` may not be modified without an
explicit decision. Adding a new `doc_status` value silently changes their behaviour** —
a new "issued" status that is not added to the `in (...)` list will make invoices vanish
from both the Products rollup and the Sales map.

## 3. Is country stored at customer level or transaction level?

**Transaction level, and this is a settled decision that must not be reversed.**

`financial_documents.country_code` is the authoritative copy, frozen at issue time exactly
as `bill_to_name` and `bill_to_gstin` are. `customers.country_code` and
`organizations.country_code` exist **only as defaults feeding the resolution chain**.

`0013`'s header states the three reasons in full:

1. A customer who relocates would rewrite their own sales history; a report run twice would
   give two answers.
2. `financial_documents.customer_id` is nullable (`on delete set null`) and the finance
   forms let you type a buyer without saving them — such a document would have no country
   at all, ever.
3. A storefront checkout has a country *before* it has a customer record.

### The resolution chain, in confidence order (`app.resolve_document_country`)

1. `customers.country_code` → `source = 'customer'`
2. `app.country_from_state(customers.state)` → `source = 'customer'`
3. `app.country_from_state(financial_documents.bill_to_state)` → `source = 'customer'`
4. `organizations.country_code` → `source = 'org_default'`
5. `null`, `null` → the widget shows an "Unspecified" bucket rather than guessing

### Two consequences for planning

- **The entity merge must repoint steps 1 and 2 to `clients`.** This is item A9 in
  `ai-context-contract.md` and item #3 in `entity-decision.md` §4. It is the **highest-risk
  item in the merge because it fails silently** — the chain falls through to
  `org_default` and the map keeps rendering, just wrong. It needs an explicit test.
- **The storefront needs no migration.** Checkout inserts with `country_code` and
  `country_source` already set; the BEFORE INSERT trigger leaves supplied values alone.
  `0013` was written for this. Do not re-plan it as schema work.

## 4. Known gaps in the two protected features

Recorded so they are not mistaken for regressions later, and not "fixed" by accident.

1. **`recurring_invoices.items` is a jsonb array with no `catalog_item_id`.**
   `orgStore.SECTIONS.fin_recurring.toRow` (`orgStore.js:337`) passes `items` through as an
   opaque array. So a product sold on a recurring invoice is attributed to the catalogue
   only if the generated invoice's line items are written with `catalog_item_id`. **Whether
   they are depends on the generation path, which does not exist server-side.** Flag as an
   open question, not a bug.
2. **`stock_qty` is never decremented by a sale.** `0011:44-51` states this explicitly and
   gives the reason: there is no goods-receipt or returns table, and a number that only
   ever falls is worse than one the operator owns outright. **Phase 3 must not "fix" this
   without adding the other half.**
3. **Neither feature has an isolation test.** `supabase/tests/01_isolation_test.sql:10-17`
   truncates 28 tables and lists **neither `catalog_items` nor `country_codes`** — the file
   predates `0011`–`0013`. So the newest, most privilege-sensitive table in the schema (the
   one with a column-level `REVOKE UPDATE`) has **zero coverage**, and nothing proves the
   `revoke` actually holds. See `definition-of-done.md` §2.
4. **Neither UI has a mobile layout.** `src/components/Products.jsx` (667 lines) and
   `src/components/dashboard/SalesByCountries.jsx` (348 lines) contain **no `768`, no
   `innerWidth`, no `matchMedia`, no `@media`** — verified by grep. Nine of the repo's 76
   components handle a breakpoint; these two are not among them. Under
   `definition-of-done.md` §4 they would not ship. **This is a gap to close, not a reason to
   redesign them** — the ask is a responsive pass, nothing more.
5. **`Products.jsx` is not committed.** Per `git status`, `src/components/Products.jsx`,
   `src/components/dashboard/`, `src/components/shared/ProductPicker.jsx`,
   `src/components/shared/CountrySelect.jsx`, `src/data/`, `src/services/catalogService.js`
   and `src/services/salesGeoService.js` are **untracked**. Committing them is a
   prerequisite for treating either feature as a fixed point.

## 5. What the Phase 3 vendor / purchase work must not break

This is the section to re-read before writing the first vendor migration.

### 5.1 Do not reuse `catalog_items` for purchased goods without a decision

The obvious move — "a product we buy is also a product, add a `purchasable` flag" — breaks
the rollups. `units_sold`, `revenue`, `revenue_paid` and `invoice_count` are defined
**exclusively over `app.catalog_is_sold()`**, which is invoices only. A purchase would
either need its own set of rollup columns, or a purchase line pointing at a
`catalog_item_id` would silently contribute nothing and the Products page would show a
product with cost and no revenue and no explanation.

**Recommendation:** if a catalogue row can be both bought and sold, add **separate,
separately-triggered** `units_purchased` / `cost` columns with their own
`app.catalog_is_purchased()` predicate. Do not widen `catalog_is_sold`. If the answer is
that purchased items are a different catalogue, say so now.

### 5.2 The `catalog_items` column-level grant is a hard constraint

`0011` does `revoke update on public.catalog_items from authenticated` followed by
`grant update (name, sku, description, category, unit_price, unit, hsn_sac, tax_rate,
track_inventory, stock_qty, low_stock_at, archived_at)`.

**Any new operator-writable column on `catalog_items` must be added to that grant list, in
the same migration.** Adding a column without it produces an UPDATE that fails from the
browser with a permission error and works from the server — the hardest kind of bug to
diagnose. `0011`'s own comment explains why it has to be a table-level revoke plus a
column-level grant and not a column-level revoke: privileges are additive.

### 5.3 Do not add a `doc_status` or `doc_type` value without updating the predicates

A purchase order or vendor bill will want a document type. Whether it lives in
`financial_documents` (with `fin_docs_type_is_financial` widened) or its own table is a
Phase 3 decision — but note:

- Widening `financial_documents` means **`fin_docs_set_country` fires on purchase orders
  too**, stamping a country on an inbound document from the *customer* chain. That is
  wrong and would pollute `sales_by_country()`, which filters by type but reads every row
  of the org (`0013`, `scoped` CTE has no type filter before the aggregate's `filter`
  clauses). Verify the `filter` clauses actually exclude the new type.
- Widening `financial_documents` also means `app.bump_usage()` (`0002:337`) counts purchase
  orders against the invoice quota, and `line_items_catalog_rollup` fires on their line
  items.

**Recommendation: purchases get their own tables.** The cost of a separate
`purchase_documents` + `purchase_line_items` is lower than the cost of auditing five
triggers and two predicates for a type they were never written to see.

### 5.4 Expense–vendor–receipt is a three-way decision, not three features

`expenses` today is description / amount / category / `incurred_on` (`0001:342`). Phase 3
wants a vendor link, a receipt attachment, and probably an approval state. These interact:

- The receipt attachment lands in `files` with `parent_type = 'expense'`
  (`document-model-decision.md` §4).
- The vendor link is the entity question in `entity-decision.md` **E6**: if a party can be
  both a client and a vendor, `clients` should be `parties` with a role now, not split
  later. **This decision must be made before the `clients` migration is written**, because
  reversing it means repointing the same two FKs a second time.
- An approval state on an expense implies who may approve — a fourth use of `member_role`
  with no UI (`feature-audit.md` #45).

### 5.5 The country chain must keep working through the merge

Repeated here because it spans both protected features and the entity decision:
`app.resolve_document_country()` reads `public.customers` **by name, twice**
(`0013:104-118`). Renaming or dropping that table without updating the function makes the
Sales by Countries map silently attribute new documents to `org_default`. **This is the
single highest-risk line item across all of Phase 1.**
